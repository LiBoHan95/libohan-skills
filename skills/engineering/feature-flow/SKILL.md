# Feature 开发流程

## 核心原则

**🛑 需求未经对齐不设计，方案未经确认不实现，实现超出 scope 不顺手修 bug。🛑**

功能开发中最大的成本是做错东西。每轮方案确认是一个强制停靠点——在用户打字说"可以"之前，不能推进到下一阶段。

**🚨 致命违规：需求模糊时直接开始实现。方案输出后不等用户确认就直接写代码。实现过程中顺手修不相关的 bug 或顺手重构。🚨**

### 证据驱动执行协议

把开发拆成可验证的小步骤，降低猜测和无关改动：

- 修改前先读取项目说明、相关实现、类型、调用方、配置和测试；不猜不存在的 API、文件或约定。
- 调研结论标明“已验证事实”“代码推断”“尚未验证”，并附具体代码或运行依据。允许表达不确定性，但影响正确性的未知项必须有验证办法，不能把推断写成事实。
- 方案必须列出改动文件、目的、测试策略、兼容性和明确不做的内容；确认前不编辑文件。
- 实现时保持最小 diff；每完成一个逻辑单元就检查类型和调用方，不一次堆积大量未经检查的代码。
- 只报告实际执行的命令和结果；失败时先分析根因，不能删除测试、放宽类型、吞掉异常或伪造通过。
- 需求、方案或实现与现状冲突时暂停，回到对应阶段重新确认，不用补丁掩盖不确定性。

## 流程

| 阶段 | 目标 | 停止条件 | 循环 |
|---|---|---|---|
| 0. 需求对齐（可选） | 将模糊需求提炼为明确的范围和验收标准 | 目标、核心场景、关键约束明确；已有确认直接沿用 | — |
| 1. 设计调研 | 调研现有模式、技术选型、影响范围 | 设计方向明确，影响范围已评估 | 可多轮 Workflow 直至信息充分 |
| 2. 方案设计 | 输出设计方案（接口、组件、数据流、迁移路径） | 用户确认方案 | 实现/验收失败可退回此处 |
| 3. 工作区准备（可选） | 确定是否需要 worktree 隔离 | 工作区就绪 | — |
| 4. 实现 | 按已确认的方案实现功能 | 功能完成，自测通过 | 方案不可行时退回 Phase 2 |
| 5. 测试 | 单元/集成/回归测试 | 测试通过 | — |
| 6. Code Review | 独立子 agent 审查改动 | 无不合理发现 | 最多 3 轮 review 循环 |
| 7. 验证 | 运行并确认功能工作的实际效果 | 用户验收 | 验收失败→退回相关阶段 |
| 8. 清理与 Git 操作（可选） | 代码清理、commit/push | 完成 | — |

## Phase 0：意图识别与需求对齐

先提取已知意图；目标、核心场景和关键约束明确时，直接进入调研，不重复发起需求确认。只对影响行为的未知项提问。

### 识别目标

1. 提取操作对象、触发条件/初始状态、可观察的预期结果，以及需要保留的现有行为。未知业务规则标为未知，前文已经确认的信息直接沿用。
2. 区分目标和实现建议。“导出选中的记录”是目标，“在前端过滤一下”是实现建议；后者需要调查可行性，不能直接当作正确方案。
3. 按行为分类：恢复已约定但失效的行为走 bug-fix-flow；新增或改变行为走本流程。混合请求分别记录目标和范围，不仅凭“bug”“添加”等词决定。纯审查或修改 skill 文本不自动套用功能开发流程。
4. 读取相关需求、测试和实现查明现状。现有代码用于理解实际行为，不能用来覆盖用户明确要求的新行为；需求来源有冲突时点明差异并澄清。

### 解决关键歧义

- 提问前可进行与歧义有关的只读调查，不需要等需求确认才能读代码。
- 不同解释会改变输出、数据范围、权限或兼容性时，询问具体行为差异；一次不超过 3 个关键问题，不询问能从项目中查明的技术细节。
- 例如“导出当前数据”：先查看页面的选择、分页和筛选语义；仍不明确时询问是选中记录、当前页还是全部筛选结果，不能自行任选一种。
- 用户提供详细技术方案时，也检查其是否明确了预期行为和验收标准；明确部分不重复确认，关键缺口仍需解决。

### 用场景核对理解

将目标写成“输入/初始状态 → 用户操作 → 预期结果”。至少覆盖一个正常场景；仅在相关时补充空数据、重复操作或失败场景。场景应包含具体例子，避免仅写“正常工作”。

```markdown
## 需求理解

**目标与操作对象**：...
**核心场景**：初始状态 → 操作 → 可观察结果。
**保留行为与约束**：...
**范围**：必须做 / 可延后 / 不做。
**待澄清问题**：仅列会改变行为的未知项；无则省略。
```

需要澄清时，将理解和关键问题交给用户确认，回复后沿用已确认内容进入 Phase 1。进入方案阶段前，目标、核心场景、关键约束必须明确；影响正确性的业务歧义需要解决。技术假设在调研中验证，不在此阶段凭空确定实现。

## Phase 1：设计调研

### 影响范围评估

在开始设计前，先评估现有环境：

1. 搜索相关模块、现有接口、已有组件——是否已有类似实现可以复用或扩展？
2. 评估影响范围：哪些现有功能可能被影响？哪些调用方需要更新？
3. 检查兼容性：新增字段/参数是否需向后兼容？是否有 breaking change？
4. 搜索关键词、类型定义、路由模式、数据模型，全面了解现有实现。
5. 检查是否有冲突中或未合并的相关分支/PR。

调研记录至少包含：可复用的现有模式、受影响的调用方、兼容性风险、测试覆盖和仍未验证的假设。每个验收场景都应对应到实际入口、数据来源和处理路径；搜索命中只用于定位，关键调用关系需读取实现核实。检查无法完成时说明限制，不把未验证项写成事实。

对影响正确性的技术假设，写明支持证据、能推翻它的结果和下一步最小检查。连续两次检查无新证据时，改变查询方向或缩小问题。只有现有证据足以支撑方案、关键假设已验证或有明确验证步骤时，才进入 Phase 2。

### 多 agent 并行调研（可选）

当功能涉及多个子系统或跨层改动时，启动 Workflow 进行多 agent 并行调研：

**触发条件（自动判断）：**

| 触发 | 不触发 |
|---|---|
| 功能跨 UI → Service → API → DB | 功能局限在单层/单文件 |
| 需要了解 3+ 现有模块的实现 | 只需搜索 1-2 个文件 |
| 有多个技术选型需要评估 | 技术方案显而易见（如现有框架的标准用法） |
| 涉及到数据迁移或 schema 变更 | 纯 UI/组件改动 |

**第 1 轮 Workflow：现状调研**

```text
Agent A：现有代码扫描
- 搜索功能涉及路径/模块的现有实现
- 列出相关文件、类型定义、路由、API endpoint
- 标注哪些文件需要修改、哪些可以复用、哪些最好不改

Agent B：影响范围分析
- 对候选改动的文件做调用方扫描（grep）
- 检查是否有测试覆盖
- 评估兼容性风险：新增字段是否影响现有调用方

Agent C：数据建模（如需涉及数据层）
- 查找相关的数据 schema、model、数据库表结构
- 查找已有的序列化/反序列化逻辑
- 如果需要新增字段，检查现有数据迁移模式
```

**第 2 轮及更多轮 Workflow：定向调研**

第 1 轮返回后，主会话分析。如果特定方向信息不足，启动第 2 轮聚焦该方向。

### 输出格式

```markdown
## 设计调研结果

**现有实现**：
- `path/to/existing.ts` — 现有模式说明
- `path/to/relevant.ts` — 可复用部分

**影响范围**：
- 需修改文件：<文件列表>
- 兼容性风险：<描述>
- 测试覆盖：<现有测试范围>

**技术选型建议（如有）**：
- 方案 A：...
- 方案 B：...

**待定事项**：...
```

调研完成后进入 Phase 2。

## Phase 2：方案设计

### 设计方法

根据功能复杂度选择设计方式：

| 复杂度 | 方法 |
|---|---|
| **简单**（单组件、单函数） | 直接给方案，不需多方案对比 |
| **中等**（多组件、新页面） | 必要时给出 2-3 个方案对比 |
| **复杂**（跨层、数据迁移、架构变化） | 先调用 `design-an-interface` skill 做多方案探索 |

### 方案内容

````markdown
## 设计方案

### 改动清单

#### 改动 1：`path/to/file.ts` — 说明
- 改动内容：...
- 设计原理：...
- 影响范围：...

### 不改的地方
- `path/to/other.ts` — 为什么不动这里

### 数据流/组件流
```
用户操作 → 组件 A → Service B → API C
          ↕
         Store D 状态更新
```

### 兼容性与验收
- 向后兼容：是/否（如否，说明迁移步骤）
- 场景对应：每个已确认行为由哪个改动实现、用什么检查验证
- 测试策略：新增/修改哪些测试
- 未验证的技术假设：验证方法、预期结果、若不成立如何调整

### 实施顺序
1. 先做 X → 2. 再做 Y → 3. 最后 Z
````

### 强制暂停点

**🚨 输出方案后，必须等待用户打字确认（如"可以"、"确认"、"按方案来"），才能进入下一阶段（Phase 3 工作区准备或 Phase 4 实现）。🚨**

如果方案涉及较大的决策点（技术选型、schema 变更、breaking change），在方案中标注待用户决策的点。

**用户确认后立即明确 scope 边界：**
```
已确认范围：
- 做：X, Y, Z
- 不做：A, B
如果在实现中发现 A 或 B 真的需要，会停下来讨论，不擅自做。
```

## Phase 3：工作区准备（可选）

方案已确认后，检查当前工作区状态，决定是否需要隔离环境来实现功能。

### 何时需要隔离

- **需要隔离**：功能涉及多文件改动、有破坏性风险、或当前工作区有未提交改动
- **无需隔离**：改动是单文件/单行改动、低风险、且当前工作区干净

### 检查步骤

1. 运行 `git status --short` 检查工作区状态
2. **如果工作区干净**（无未暂存或已暂存的改动）：如果改动范围小且低风险，可以直接跳过隔离进入 Phase 4。如果改动涉及多处或有破坏风险，询问用户是否要创建 worktree
3. **如果工作区有未提交改动**：

基于已确认的方案告知用户改动范围，并提示：

```
当前工作区有未提交改动，建议隔离本次开发。

请选择：
[1] 在新 worktree 中开发（推荐） — 完全隔离，互不影响
[2] 先提交当前改动 — 结束上个工作
[3] 继续在当前工作区 — 改动将混在一起
```

### 选项处理

**选项 1：创建 worktree**

- 询问 worktree 的基线分支
- 建议分支名：`feat-{描述}`（如 `feat-search-filter`）
- 调用 `EnterWorktree` 工具创建隔离工作区
- 进入 Phase 4

**选项 2：提交当前改动** — 完成提交后进入 Phase 4

**选项 3：继续在当前工作区**

- 警告："改动将与现有改动混在一起。"
- 记录"在脏工作区中继续"

### 注意事项

- 如果已在 worktree 中，跳过此阶段
- 如用户在 CLAUDE.md 中有 worktree 偏好，按偏好执行

## Phase 4：实现

### 实现原则

- 只做方案确认的内容
- 不改动设计方案外的东西
- 不顺手修 bug（即使看到明显 bug，记录位置但不修改——除非用户单独要求）
- 不顺手重构（重构应在单独的任务中完成）
- 保持向后兼容（除非方案明确写明了 breaking change）

实现前再次核对已确认 scope 和文件清单，并运行项目实际存在的相关检查，记录修改前基线：命令、结果及已有失败；不能运行时说明原因。不要到修改完成后才声称建立了修改前基线。

每个逻辑单元完成后查看 diff 并运行最相关的检查；如果发现方案不可行或范围扩大，立即停止并回到 Phase 2。

### 测试先行

默认不要求 TDD，但以下场景建议先写测试再实现：

1. 涉及核心逻辑或数据转换
2. 涉及 API 接口行为变化
3. 涉及竞态条件或异步处理
4. 涉及复杂条件分支

如果当前项目启用了 `tdd` skill 习惯，可以调用 `tdd` skill 进行测试驱动开发。

### 自测

实现完成后，运行最小验证确认功能按预期工作：

1. 编译/类型检查通过
2. 功能基本路径可跑通
3. 单元测试通过

## Phase 5：测试

### 执行步骤

1. 对照 Phase 4 修改前记录的基线，区分原有失败与本次新增失败
2. 新增或修改测试覆盖已确认的行为场景，检查断言是否真正观察预期结果
3. 运行所有相关测试及必要的调用方回归，记录实际命令和结果；缺少运行条件时标记未验证

测试或类型检查失败时，先记录失败命令、首个相关错误和新的诊断假设，再修改代码。连续失败或行为变化时回到调研，禁止重复盲改。

### 改动影响到的测试文件

如果有新测试可以写，先确认它能在改动前暴露"旧行为"（如果适用），再验证改动后通过。

## Phase 6：独立 Code Review

实现和测试完成后，必须在独立子 agent 中调用 `code-review` skill。

1. 启动 `general-purpose` subagent，prompt 中要求其调用 `Skill` 工具加载 `code-review` skill
2. 提供：
   - review 的固定起点（commit、branch、tag 或 merge-base）
   - 原始需求描述和预期行为
   - 已确认方案
   - 本次改动文件
   - 只审查不修改代码
3. 主会话核实 findings。修复有效问题后启动新的独立子 agent re-review。最多 3 轮。

推荐 prompt：

```text
这是一次功能开发审查。请先调用 Skill 工具加载 code-review skill，再按其流程审查从 <fixed-point> 到当前工作区的改动。
需求：<description>
预期行为：<expected>
已确认方案：<plan>
本次改动文件：<files>
只审查，不要修改文件；返回经过验证的 findings。
```

## Phase 7：验证

### UI/功能验收

如果功能涉及可见/可交互的 UI，给用户最简短明确的验收步骤：

```markdown
## 请你验收

代码层验证已通过，请在实际环境确认：

1. ...
2. ...
3. ...

**预期结果**：
- ...
- ...

**代码验证结果**：
- [通过] ...

**尚未由 Claude 验证**：
- 真实环境中的上述完整流程
```

用户确认通过后才能记录"验收通过"。

**如果验收失败**：回到与反馈最相关的阶段，不做猜测式补丁。
- 需求理解偏差 → 回到 Phase 0 重新对齐需求
- 方案方向不对 → 回到 Phase 2 重新设计方案
- 实现细节有问题 → 回到 Phase 4 修复实现
- 测试遗漏 → 回到 Phase 5 补充测试

验收失败后，只做退回阶段对应的修正工作，不降级为随意补丁。

## Phase 8：清理与 Git 操作

### 代码清理

- 检查是否有 debug log、console.log、注释掉的代码、TODO 标注
- 移除临时文件
- 确认无死代码，并检查最终 `git diff` 只包含已确认 scope

### 向后兼容检查

最终确认新代码不会破坏现有调用方：
- 检查新增的 public API/组件是否正确导出了
- 检查是否有未使用的 import 或类型
- 检查文档（README、类型注释）是否需要更新

### Git 操作

Git 操作需要独立、明确的授权。用户不开口就不提交不推送。

**Commit 消息格式**：
```
feat: 【模块名】描述
```

第二行起加详细说明（每行用 - 开头）。

仓库已有 commit 规范优先于本格式。

## 完成汇报

流程允许结束时，按“结果、修改、验证、风险”四项汇报；验证只写实际命令和结果，未完成或未验证内容必须明确标出。

### Worktree 清理

如果本次开发在 worktree 中：

1. 提示："开发已完成并推送，是否退出 worktree？"
2. 选项：
   - **[删除]**：`ExitWorktree` 参数 `action="remove"`
   - **[保留]**：`ExitWorktree` 参数 `action="keep"`

**异常退出**：如果中途放弃开发，worktree 中有未提交改动时：
- 提示："worktree 中有未提交改动，是否保留？[保留/删除并丢弃]"
- 删除时传入 `discard_changes=true`

## 红旗：立即停止

- 影响正确性的业务歧义未解决就进入设计或实现（只读调查可以先进行）
- 方案输出后未经用户确认直接写代码
- 实现过程中顺手修了无关 bug 或顺手重构
- 将推断当作已验证事实，或关键不确定项没有验证办法；允许表达不确定性，业务歧义先澄清，技术假设先验证
- 验收时仅凭类型检查或测试通过就声称功能已正确
- 把方案确认或验收确认当作 Git 授权
- 用户反馈不符合预期后继续猜测式补丁（应回到 Phase 1）
- 将 scope 之外的改动混入本次提交
- 实现中发现方案不可行但继续硬做（应回到 Phase 2 更新方案并重新确认）
- 在脏工作区中直接开始开发未告知风险

出现任一项，回到对应阶段修正。

## Known Gotchas

- **"加个简单功能"实际涉及 3 层**：用户说"加个排序"，实际要 API 支持排序参数 + 后端逻辑 + 前端交互。在 Phase 0 需求对齐时就拉平认知，避免方案阶段才发现 scope 远超预期。
- **兼容性确认只在方案阶段做，验证时不核实**：方案写了"向下兼容"，但实现时改了接口签名没更新调用方。Phase 7 验证必须回归调用方。
- **测试只跑新增文件**：新增了 3 个文件、改了 1 个现有文件，只跑新增的 3 个测试不跑回归。Phase 5 必须跑完整测试集或改动影响到的全部测试。
- **实现结束时声称"功能完成"但没自测**：编译通过不等于功能可用。Phase 4 的"自测"是跑通核心流程，不是只看编译。
- **scope 蔓延在实现阶段无声发生**：做功能 A 时发现"顺便加个 B 也很合理"——但 B 没在方案里。回到 Phase 2 更新方案或标记 B 到后续迭代。
- **worktree 中实现的功能推到错误分支**：worktree 创建时指定的基线分支不对，推送时 PR 的目标分支混乱。Phase 3 确认基线分支，Phase 8 推送前再次确认目标分支。
