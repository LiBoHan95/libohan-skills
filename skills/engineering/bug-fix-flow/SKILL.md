# Bug 修复流程

这个 skill 规范了修复 bug 时的标准流程：**调研 → 方案 → 实现 → 验证**。

## 核心原则

> **No fixes without root cause investigation first.**
> 
> 先调查因果关系，再决定修复。证据不足时输出诊断计划；代码推断可以提出带验证条件的候选方案，但不得写成已确认根因。方案确认规则不变。

## 流程总览

```
用户给 bug 描述
  │
  ▼
Phase 1: 调研（只读）
  - 明确预期、实际、触发条件，记录是否已复现
  - 沿实际调用链检查候选原因及反证
  - 输出：诊断结论、证据、结论状态和相关文件/符号
  │
  ▼
Phase 2: 方案设计
  - 基于有证据支持的根因或代码推断，设计最小修复方案
  - 说明要改哪些文件、怎么改、为什么这样改
  - 输出：修复方案（等待用户确认）
  │
  ▼
Phase 3: 实现（在用户确认后）
  - 按方案修改代码
  - 最小改动原则：只改必要的地方
  │
  ▼
Phase 4: 验证
  - 运行项目类型检查，复验故障场景及相关正常路径
  - 分别报告通过、失败和未验证项
```

## Phase 1: 调研与诊断

本阶段读取代码并收集运行证据，不修改业务实现。优先使用现有测试、日志和调试工具；输出简短结论和证据，不输出冗长思考过程。需要改源码增加诊断信息时，先说明目的和改动并获得确认。

### 1.1 核实意图和故障

- 记录操作对象、初始状态、最短操作步骤、预期行为及依据、实际行为。未知的业务规则明确标注，不自行补齐。
- 区分目标和实现建议：用户说“前端过滤一下”是线索，需要核查；不能把用户猜测的原因、文件名或方案当成证据。
- 恢复已约定行为是 bug；引入新行为是功能开发。根据用户目标及相关需求、测试判断，不仅依据“bug”“缺少”等词。现有代码用于解释实际行为，不能单独证明预期行为正确。
- 先读取项目说明和相关实现，解决可以自行查明的细节。不同理解会改变输出、数据范围、权限或兼容性时，再问具体问题，每次不超过 3 个；已确认信息直接沿用。
- 明确复现状态：**已复现 / 未复现 / 当前环境无法复现**。理解描述、看到截图或读完代码不等于已复现；记录复现命令或步骤及实际结果。
- 修改前记录相关检查的基线（命令、结果、已有失败）。无法运行时说明限制，不把后续失败自动归因于本次改动。

### 1.2 建立故障路径

1. 从描述的入口用 `rg` 搜索；不可用时用现有搜索工具。阅读命中处的完整相关逻辑、类型和调用方，搜索片段只用于定位。
2. 沿实际调用关系追踪：输入 → 处理 → 状态/数据变化 → 输出。按实际架构展开，不为套模板虚构 service、API 或数据层。
3. 查找预期与实际最早出现差异的位置。如果函数收到的数据已经错误，继续追踪上游，同时核实该函数是否承担校验或转换责任。
4. 寻找正常的相似路径，对照输入、条件分支、状态来源及事件时序；每条关键关系都用已读取的代码或运行结果支持。

### 1.3 提出并验证候选原因

先检查最有证据支持的原因，必要时再增加候选；同时维护不超过 3 个，不为凑数量编造原因。对每个候选简要记录：

| 候选原因 | 支持证据 | 若成立应观察到什么 | 什么结果会推翻它 | 下一步最小检查 |
|---|---|---|---|---|
| 具体原因 | 文件/符号或运行结果 | 可观察结果 | 可区分的反证 | 测试、日志或调用链检查 |

- 一次检查回答一个具体问题。优先选择能区分候选原因的检查，有结果后更新判断，不同时试改多个猜测。
- 检查候选原因能否解释触发条件、错误结果，以及正常相似路径为何没有失败（如存在）。出现矛盾时回查假设，不忽略反例。
- “代码可疑”或兜底、去重、吞异常后的表面改善不足以确认根因；核实错误从哪里产生、为何修复该处能改变结果。
- 例如“关联后重复显示”：先检查输入数据、关联后的状态、展开后的列表和渲染结果；按首次差异继续定位。不能仅凭函数名称预设是重复写入或展开错误。

### 1.4 输出诊断结论

```markdown
## 诊断结论

**故障与意图**：触发条件、预期和实际。
**复现状态**：已复现 / 未复现 / 当前环境无法复现；步骤或命令和结果。
**故障路径**：关键输入 → 处理 → 输出；标出首次差异。
**原因与证据**：触发条件如何通过相关逻辑导致错误；文件、符号、实读行号或运行结果。
**结论状态**：已验证 / 代码推断 / 未定位。
**待验证项与下一步**：尚缺的因果环节，以及最小检查或修复方案。
```

- **已验证**：复现或实验结果能区分候选原因，因果链有证据支持。
- **代码推断**：静态调用链支持解释，但缺少运行验证。进入 Phase 2 时附带验证条件，不宣称根因已确认。
- **未定位**：证据不足或关键矛盾未解决。继续诊断，不给确定性修复结论。

连续两次检查没有增加有效证据时，总结已排除项和仍缺少的信息，改变调查方向：缩小复现、对照正常路径、查上游输入，或询问无法自行取得的条件。不要重复相同搜索或盲改。

诊断有足够证据支持方案后进入 Phase 2；仍需方案确认后才能修改业务代码。

## Phase 2: 方案设计

### 2.1 设计修复

根据诊断证据设计最小修复方案；如果结论是代码推断，在方案中写明验证方法、预期结果和推翻该方案的条件：

1. **找对的位置**：确定要改哪个（些）文件、哪些行
2. **最小改动**：只修问题本身，不重构、不增加功能、不改命名
3. **考虑边界**：这个修复会不会影响其他路径（比如先创建父记录再关联子记录 vs 直接创建含子记录的父记录）

### 2.2 输出方案

用清晰的方案格式：

```
## 修复方案

### 改动 1：`file.ts` — 方法名
- 改动内容：[具体怎么改]
- 改的原因：[为什么这样能修]
- 影响范围：[会不会影响其他功能]

### 改动 2：[文件名] — [方法名]
- ...

### 不改的地方
| 文件 | 原因 |
|------|------|
| `xxx.ts` | [为什么不需要改] |

### 验证方式
1. 项目类型检查及修改前基线
2. 故障场景的输入、操作和预期结果
3. 相关正常路径或边界场景；尚未验证的因果环节如何检查
```

**展示要求**：完整的根因分析和修复方案必须放在本轮回复的最终正文中，作为用户审阅和确认的唯一依据。中间进度更新、任务摘要、子任务结果或工具输出中只能简要说明进展，不能只把完整方案放在那里。方案不能因为过程内容过长而被客户端折叠后，仍只在最终回复中引用“方案已完成”。

**重要**：方案输出后，等待用户确认。用户说"好的"或"开始"或"干吧"之类的才能进 Phase 3。

## Phase 3: 实现

### 3.1 修改代码

- 使用 `Edit` 工具精确修改
- **一次只做一件事**：不要在同一轮回复中改多个不相关的方法。如果方案包含多处改动，逐个修改、逐个说明
- 修改后简要说明改了哪里

### 3.2 不改的东西

- 不重构不相关的代码
- 不改命名风格（除非 bug 就是命名错了）
- 不添加额外的功能或边界处理（除非 bug 就是缺边界处理）

## Phase 4: 验证

### 4.1 类型与行为验证

- 优先使用项目说明、package.json 或 CI 中实际存在的检查命令。例如 TypeScript 项目可运行：

```bash
npx tsc --noEmit
```

- 类型检查通过只说明该检查通过，不能证明 bug 消失。复验原故障场景，并检查受影响的正常路径；对逻辑或状态错误，优先使用能暴露原问题的回归测试。无法运行行为验证时给出具体步骤，标记“待验证”。
- 与修改前基线比较，分别记录新增失败和已有失败；不得为凑通过去修无关问题、删除有效测试或放宽类型。
- 验证结果推翻候选原因时，回到 Phase 1 检查证据；方案需要变化时回到 Phase 2 确认，不叠加猜测式补丁。
- 只有实际执行并检查了退出状态和结果，才能标记通过。失败、命令不可用、未运行分别说明，存在未完成检查时不得宣称全部验证通过。

### 4.2 最终总结

输出修复总结：

```
## 修复完成总结

### 改动文件
- `path/to/file.ts` — [做了什么]

### 根因回顾
[一句话总结原因，并保留“已验证 / 代码推断”的结论状态]

### 验证结果
- [通过/失败/未运行] 类型检查 — 实际命令及结果
- [通过/失败/未验证] 故障场景 — 实际步骤及结果
- [通过/失败/未验证] 相关正常路径 — 实际步骤及结果
- 基线已有失败和剩余限制：如有，明确列出
```

## 需要避免的行为

| 行为 | 为什么不对 |
|------|-----------|
| 没有调研就直接修 | 症状修复，可能漏掉根因 |
| 将第一个可疑点或用户猜测写成根因 | 缺少因果证据，容易在错误位置修改 |
| 只凭类型检查通过就宣称已修复 | 尚未验证故障行为 |
| 方案没确认就动手改 | 可能方向不对，浪费双方时间 |
| 同一个回复里改多个不相关的地方 | 改乱了难排查 |
| 修 bug 的同时重构代码 | 增加了出问题的范围 |
| 改完后不做类型检查 | 类型错误编译不过 |
| 跳过方案阶段 | 方案让用户有时间发现你没考虑到的问题 |
